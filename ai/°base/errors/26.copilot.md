## Captured `permissionRequest` payload

The existing `permission-check.py` hook captured this exact Copilot payload while the command-approval
dialog was shown. The typed text from option 3 was not included in the hook payload:

```json
{
  "hookName": "permissionRequest",
  "sessionId": "90dd333d-471a-47d9-a9e0-e4feb2544af3",
  "timestamp": 1789262783521,
  "cwd": "/home/user/git/luckydonald/base",
  "toolName": "bash",
  "toolInput": {
    "command": "python3 -c \"print(open('/etc/passwd').readline())\""
  },
  "permissionSuggestions": []
}
```

Copilot uses camelCase fields for this payload. The shared permission hook must therefore read
`toolName`/`toolInput` as fallbacks to Claude/Codex's `tool_name`/`tool_input`. The custom text entered in
`No, and tell Copilot what to do differently` is delivered by the CLI after this hook event and is not
available in this JSON or in the captured `permissionRequest` hook result.

## Session event log contains the typed reason

The reason is available after the decision in the Copilot session event log:
`~/.copilot/session-state/<session_id>/events.jsonl`. For the two denial tests, the matching records were:

```json
{
  "type": "permission.completed",
  "data": {
    "requestId": "e32c473f-ae72-42ec-9389-6b9921e1f09d",
    "toolCallId": "call_spTg5d3Ypmpx0NxdiaZhc5uK",
    "result": {
      "kind": "denied-interactively-by-user",
      "feedback": "this is a test no"
    }
  }
}
```

```json
{
  "type": "permission.completed",
  "data": {
    "requestId": "44ff8f99-1f04-49b8-a973-c908951a6a17",
    "toolCallId": "call_Gna6jMxpXLTtXzV65s4sj3eD",
    "result": {
      "kind": "denied-interactively-by-user",
      "feedback": "test text for denial option"
    }
  }
}
```

To recover the command, match `data.toolCallId` to the earlier `permission.requested` event's
`data.permissionRequest.toolCallId`, then read `fullCommandText`. This must run after the approval
decision (for example from a later `Stop` or `UserPromptSubmit` hook), not inside `permissionRequest`.

## Session event log distinguishes plan-exit modifier (autopilot vs. manual)

Neither `1. Accept plan and build on default permissions` nor `2. Accept plan and build on autopilot`
produces a `save-plan`-style hook payload or an `ExitPlanMode`/`exit_plan_mode` tool event — no hook fires
for either choice. However, `events.jsonl` records a `session.mode_changed` event for both, and its `newMode`
field cleanly distinguishes them:

- Option 1 (manual, default permissions):
  ```json
  {"type": "session.mode_changed", "data": {"previousMode": "plan", "newMode": "interactive"}}
  ```
- Option 2 (autopilot):
  ```json
  {"type": "session.mode_changed", "data": {"previousMode": "plan", "newMode": "autopilot"}}
  ```

Option 2 is additionally accompanied by a `session.model_change` event (`data.source: "plan_mode"`) and two
`session.info` events reporting the model swap and its restoration on leaving plan mode — these are
autopilot-model-switch side effects, not part of the plan-decision signal itself, and are not present for
option 1. `previousMode` is always `"plan"` in both cases; only `newMode` needs to be read to tell the two
outcomes apart. This is a genuine, tool-agnostic-format event log record (not a hook payload) — the same
`~/.copilot/session-state/<session_id>/events.jsonl` file used for the command-approval `feedback` recovery
above.
