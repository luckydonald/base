## Findings

**1. No env-var substitution for http headers in `°settings_lib`.** `mcp_servers.py` copies `headers` verbatim into every rendered target — `render_claude_mcp` (line 117: `entry["headers"] = dict(server["headers"])`), the parse-back path (line 140), and Codex's TOML (`_server_table_lines`, line 186: `lines.append(f'http_headers = {json.dumps(headers)}')`). Whatever string you put in `settings.json`'s `headers` ends up byte-for-byte in `.mcp.json` and `config.toml`.

**2. No expansion mechanism confirmed usable either.** `mcp.schema.json` (`ai/settings/mcp.schema.json`) just types `headers` as `additionalProperties: {type: string}` with no mention of interpolation; there's no comment/doc anywhere claiming Claude Code's native `.mcp.json` expands `${VAR}` inside `headers`. No example of this pattern exists in the repo to confirm or refute Claude Code's own runtime behavior — this project has never relied on it.

**3. No precedent for authenticated `http`-type servers anywhere.** `grep -rn '"type": "http"\|"headers"'` across all six `.mcp.json` files and `ai/settings/settings.json` returns zero hits — every current server (`bugsink`, `chrome-devtools`) is `type: "stdio"`. The only secret-injection precedent is the `.env` tools wrapper (`ai/settings/settings.json`'s `mcp.tools[".env"]`, using `envmcp --env-file ai/.env`/`mcpipe --debug`), which per the schema's own `tools` description only prepends argv tokens — it cannot reach into `url`/`headers`. There is no author precedent for solving this problem for `http` servers; this would be a first.

**4.
