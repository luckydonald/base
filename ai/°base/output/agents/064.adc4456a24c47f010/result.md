### 1. What `link_subproject.sh` does
Purely symlink/scaffolding plumbing for the monorepo case (`scripts/°base/init/link-subproject-claude.sh:1-30, 220-230`): symlinks `.claude`, `.codex`, `ai/settings`, `ai/references`, `ai/skills`, `.mcp.json`, and each `.run/*.run.xml` from the linked subfolder to the git-root counterparts; touches `.gitkeep` in `ai/errors`, `ai/output/agents`, `ai/output/explore`, `ai/plans` (note: **not** `ai/memory`, line 170); seeds `ai/query.md`/`CLAUDE.md` from templates; symlinks `AGENTS.md → CLAUDE.md`. Because `.claude` is symlinked wholesale, `.claude/settings.json` (which registers the `record-memory` hook for `PostToolUse`/`SessionStart`, `.claude/settings.json:38-99`) is identical for the subfolder and the root — **hook registration is not missing** for a linked subproject.

### 2/3. How `record-memory/hook.py` resolves paths
- Source dir: `_encoded_project_dir(subproject)` (`_lib.py:363-369`) = `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<subproject-path-with-non-alphanumerics-replaced-by-"-">/memory`. This regex-based encoding matches Claude Code's real encoding (a prior underscore-related mismatch was already fixed, see `ai/°base/plans/012_fix-record-memory-hook-misses-paths-with-underscores.md`).
- `subproject` = `_subproject_root()` (`_lib.py:372-377`): **`os.environ.get("CLAUDE_PROJECT_DIR") or os.getcwd()`** — explicitly documented as "the directory Claude was launched from," i.e. fixed at session start, not re-derived from whatever directory you later `cd` into inside the same session.
- Destination dir: `memory_lib.memory_dirs(subproject)` (`°memory_lib/dirs.py:11-26`) → `<subproject>/ai/memory` (primary) unless `subproject` is the `base` meta-repo itself, in which case it's `<subproject>/ai/°base/memory`.
- `links.py`'s `link_file`/`same_inode` hardlink first (`os.link`), falling back to `symlink_to` on `OSError` (e.g. cross-filesystem) — `destination.parent.mkdir(parents=True, exist_ok=True)` (`links.py:42`) means the destination `ai/memory/` dir is auto-created on first write, so the missing `.gitkeep` for `ai/memory` in the link script is **not** fatal by itself.

### 4. `link-subproject-claude.sh` and memory
It does not touch memory at all — no `ai/memory/` scaffolding, no `MEMORY.md` seeding (confirmed no `MEMORY.md` template exists under `scripts/°base/init/templates/`, only `CLAUDE.md`/`query.md`). This appears intentional: `MEMORY.md`/individual memory `.md` files are meant to be Claude-authored (written to `~/.claude/.../memory/`) and then mirrored in by the hook, exactly like any other memory file — not pre-seeded.

### 5/6. Empirical reproduction — no registration step is missing, but a real failure mode exists
I built an isolated throwaway git repo, copied the real `scripts/°base` + `.claude/settings.json` into it, created a subfolder, ran the real `link-subproject-claude.sh` against it, then invoked the real `record-memory/hook.py` exactly as `.claude/settings.json` would (`python3 .../hook.py` with a `PostToolUse` JSON payload), with `CLAUDE_PROJECT_DIR` set to the subfolder and a fake Claude memory file placed at the correctly-encoded `~/.claude/projects/<encoded-subfolder>/memory/*.md`. **It worked correctly** in every variant I tried (default config dir, and an explicit `CLAUDE_CONFIG_DIR` matching the multi-account setup described in `project_dual_codex_config_dirs.md`): the memory file was hardlinked into `<subfolder>/ai/memory/` and auto-committed (`ai: record memory <name>`). So the hardlink/commit machinery itself, `link_subproject.sh`'s scaffolding, and the hook registration are **not** broken for a properly-invoked subproject session — there is no missing "registration" step in this repo's scripts.

### Root cause I actually believe explains the user's symptom
`_subproject_root()` is pinned to **wherever the `claude` process was launched from** (`CLAUDE_PROJECT_DIR`), not to whatever directory you're currently focused on/`cd`'d into within an existing session. If a user:
1. already has a Claude Code session running with `CLAUDE_PROJECT_DIR` = the monorepo root (or any other existing project dir), and
2. creates a new subfolder and runs `link_subproject.sh` from a separate shell, but
3. keeps working inside that **same, already-running** Claude Code session instead of starting a fresh `claude` process with cwd = the new subfolder,

then every hook invocation for that session still resolves `_subproject_root()` to the *original* launch directory. `_encoded_project_dir()` therefore points at the original session's `~/.claude/projects/<root-encoded>/memory/`, and `memory_dirs()` computes `dst_dir` = `<root>/ai/memory` (or `ai/°base/memory`) — never the new subfolder's `ai/memory/`. The new subfolder's own memory directory is never touched by that session at all, which looks exactly like "the new subfolder can't save memories," even though nothing is actually broken — restarting `claude` with the subfolder as cwd (as the script's own usage comment implies: `cd monorepo/some_project`) would make `CLAUDE_PROJECT_DIR` match and the sync would work exactly like it did in my repro.

### Secondary, already-documented but separate bug
`project_dual_codex_config_dirs.md` documents that `record-memory/hook.py` **was** fixed to respect `$CLAUDE_CONFIG_DIR` (`_lib.py:353-360`), but `scripts/°base/ai/memory/delete.py`'s own duplicated `_encoded_project_dir()` was **not** updated and still hardcodes `~/.claude`. This is a real, still-open bug, but it affects the memory-delete CLI for any repo, not something specific to newly-linked subfolders.
