# Improve lplp commit style: fold the final plan revision into the run commit

## Context

`ai/skills/commit-with-lplp-style/SKILL.md` currently treats *every* genuine plan revision as its own kept commit (`ai: Plan:` for the first version, `ai: Plan update:` for each later one), and only folds a plan commit into the implementation when its content turned out unchanged/near-identical to the version before it. In practice this produces history like:

```
ai: Plan: ...
ai: Plan update: ...
ai: Plan update: ...
ai: Run: ...
```

even for a single-shot plan-then-run, where it produces:

```
ai: Plan: ...
ai: Run: ...
```

The user wants the *last* plan revision — the one that actually becomes the implementation — to always fold into the run commit instead of staying separate, since the run commit's summary/body already describes the final state of the plan plus the code that implements it. Only genuinely earlier revisions (the ones superseded by a later plan update before implementation ever happened) should still be kept as separate history. Concretely:

- Plan → update → run: keep the first plan version separate, fold the second (final) revision into the run commit, with a short note in the run commit's body about what changed in that final revision.
- Plan → run (never revised): the single plan version folds entirely into the run commit — one commit total, not two.

This changes the fold criteria described in three spots of the skill doc, plus the illustrative rebase-todo template. `.claude/commands/commit-with-lplp-style.md` is a generated shim (`<!-- Generated by scripts/°base/ai/settings/sync.py; do not edit directly. -->`) that only points at the skill file and contains no fold logic of its own — it does not need touching. `ai/°base/AGENTS.md` only references the skill's rule 9 (noting activation in the plan file) and is unrelated to this change.

## Changes to `ai/skills/commit-with-lplp-style/SKILL.md`

**1. "When to keep a commit separate instead of folding" bullets (currently lines 29–35).**
Replace the first two bullets (genuine-change-stays-separate, and revision-history-stays-separate) with:
- The plan revision immediately preceding the implementation — the one that actually becomes code — always folds into the run/implementation commit, even when it's itself a genuine, substantive change over the version before it. It doesn't need its own commit: the run commit's summary already covers it (de-conjugated per the existing summary-line rule), and its body should note what changed in that final revision when it differed from the last kept plan version.
- Every *earlier* revision of the same plan number — one followed by at least one further plan-file revision rather than directly by the implementation — stays its own commit; folding it would erase the revision history. Keep each as `ai: Plan:` (first) or `ai: Plan update:` (each later one, up to but excluding the final pre-run revision).

Leave the byte-identical/near-identical bullet and the same-drafting-burst-squash bullet as is (they still govern whether an earlier revision counts as "genuinely distinct" in the first place), and leave the prompt-commit and "when in doubt, fold" bullets unchanged.

**2. "Naming a plan-only commit that is kept separate" (currently lines 37–44).**
Add one clarifying sentence noting this naming/rename procedure applies only to the kept earlier revisions — the final pre-run revision is never renamed on its own because it folds into the run commit instead.

**3. "Cleaning up stray `ai:` auto-commits" — Plan commits bullet (currently line 119).**
Reword to match point 1: the revision immediately before the implementation commit always folds into it (noting the change in the run commit's body when relevant); earlier revisions each stay their own renamed `pick`.

**4. Procedure step 2, "Plan groups" bullet (currently line 135).**
Same reword: final pre-implementation revision always fixes up into the implementation; earlier genuinely distinct revisions keep separate, renamed picks; unchanged/near-identical revisions fold into whichever kept version precedes them (or into the implementation, if they're the one immediately before it).

**5. Rebase-todo template (currently lines 148–167).**
Update the plan-commit portion of the illustrative template from:
```
pick <plan-commit>             # plan with follow-up updates: keep separate
# fixup <plan-commit>         # lone plan (no updates): may fold into implementation
pick <next-code-commit>
fixup <prompt-commit>
```
to something like:
```
pick <plan-commit-v1>          # earlier revision, superseded by a further plan update: keep separate
exec git commit --amend -F ai/git/rebase-msg-<sha>.md
pick <next-code-commit>
fixup <plan-commit-vN>         # final revision immediately before this implementation: always fold
fixup <prompt-commit>          # ai: updated prompt; backward-fold
...
```
with a short note that a plan revised more than twice repeats the `pick` + `exec ... --amend` pair for each additional kept earlier version, and that a plan never revised at all skips the `pick <plan-commit-v1>` lines entirely — its single plan commit is just another entry in `<next-code-commit>`'s fixup group alongside the prompt/decision/agent/memory commits.
